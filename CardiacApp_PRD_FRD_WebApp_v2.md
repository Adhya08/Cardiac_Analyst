# **1\. Executive Summary**

This document defines the complete Product Requirements (PRD) and Functional Requirements (FRD) for a web-first cardiac risk prediction platform. The system operates in three integrated modes: Routine Screening, ECG-Enhanced Diagnosis, and Emergency Triage.

The platform is re-architected from a mobile-native design to a Progressive Web Application (PWA) built with React 18 + TypeScript, making it instantly accessible on any device — desktop, tablet, or mobile — with no app-store installation required. This accelerates deployment, lowers adoption friction, and allows clinics and hospitals to embed the tool directly into their existing web portals.

Key improvements in v2.0 over the original concept include: upgraded ML accuracy targets, browser-native ECG signal processing, WebRTC-based real-time vitals logging, a richer explainability dashboard, and a redesigned emergency UX optimized for desktop and touch.

## **1.1 Problem Statement**

- Cardiovascular disease is the leading cause of death in India, claiming 4.77 million lives annually.
- Most patients self-present at ER stages when damage is irreversible — early digital screening tools are a critical gap.
- Existing consumer web tools offer only static risk calculators with no ECG analysis, diagnostic explanation, or emergency routing.
- ECG interpretation remains scarce outside hospital settings; a web app deployable by any clinic democratizes access without hardware barriers.
- Progressive Web Apps (PWAs) can reach patients on low-end Android handsets via Chrome without requiring app store access — crucial for Tier 2/3 India.

## **1.2 Solution Vision**

A single browser-based platform that acts as a 24/7 personal cardiac monitor — logging daily vitals, escalating to ECG-based diagnosis when needed, and activating a full emergency response stack (hospital finder + ambulance dispatch) in crisis moments, all with AI-generated plain-language explanations of every finding, accessible from any device via a URL.

# **5\. Functional Requirements Document (FRD)**

## **5.1 Mode 1: Routine Screening Flow**

1.  User visits the web app URL and authenticates via phone OTP. JWT stored in httpOnly session cookie.
2.  Dashboard loads with persistent header showing: Logo | Risk Level badge | SOS button (always visible) | Menu.
3.  User navigates to 'Daily Check-In' — a clean card-based form rendered with React Hook Form + Zod validation.
4.  Vitals form fields: Weight (kg), Systolic BP (mmHg), Diastolic BP (mmHg), Heart Rate (bpm), SpO2 (%), optional: Fasting glucose (mg/dL), Total cholesterol (mg/dL).
5.  Client-side validation: BP 60–250 mmHg, HR 20–250 bpm, SpO2 40–100%. Out-of-range values show inline error with guidance. No submission until valid.
6.  On submit: POST /api/v1/vitals. Response includes risk_score, risk_tier, trend_delta, and ecg_prompt flag.
7.  LightGBM model runs server-side: today's vitals + profile (age, sex, smoker, diabetic, family history) + 30-day rolling average + Indian cohort calibration coefficients.
8.  Risk tier returned: Low (&lt;7.5%), Borderline (7.5–15%), Elevated (&gt;15%). Displayed as colour-coded progress arc with confidence interval.
9.  SHAP explainability panel renders: horizontal bar chart of top-5 contributors with labels like 'Systolic BP: +18% to your score'. Powered by SHAP values from model inference.
10. IF score ≥ Elevated OR red-flag symptom declared → ECG Escalation banner displayed prominently with 'Upload ECG' CTA.
11. ELSE: 30-day trend chart (Chart.js) shows BP, HR, weight, SpO2 over time. Lifestyle tip card shown. Next check-in reminder set via Web Push API.

## **5.2 Mode 2: ECG-Enhanced Diagnostic Flow**

1.  ECG Prompt screen: 'Your vitals suggest we should look more closely. Get a 12-lead ECG at a nearby clinic and upload it here.'
2.  'Find ECG Clinic Near Me' button opens Google Maps embed filtered to 'ECG clinic' within 10 km using browser geolocation (Geolocation API).
3.  Upload section: Drag-and-drop zone using React Dropzone. Accepted formats: JPG, PNG, PDF (scanned ECG report), CSV (KardiaMobile / Apple Watch export).
4.  Client-side: file size validation (max 20 MB), format check, loading spinner with step-by-step status: 'Uploading... Extracting signals... Analysing...'
5.  Server-side image preprocessing (OpenCV + NeuroKit2): deskew → grid removal → 12-lead region detection → signal extraction per lead → resample to 500 Hz, 10 seconds per lead → normalize to \[-1, 1\].
6.  ECG Ensemble Classification: 1D-SE-ResNet (PTB-XL trained) + Transformer (CPSC+Georgia trained) → ensemble via soft voting → probability vector for 15 condition classes.
7.  Decision thresholds: prob > 0.85 = DETECTED (red badge), prob 0.50–0.85 = POSSIBLE (amber badge), below 0.50 = NOT DETECTED (grey).
8.  Fusion scoring: Final_Risk = 0.3 × Tabular_Score + 0.7 × ECG_Score. STEMI override: if ECG_STEMI_prob > 0.85 → force Emergency Mode regardless.
9.  IF STEMI or VT detected: automatic redirect to Emergency Mode — full-screen alert, no user action required.
10. GradCAM heatmap computed via tf-explain: red/orange overlay on ECG image highlights abnormal segments (e.g., ST elevation in leads II, III, aVF highlighted in red). Overlay rendered as interactive SVG layer in browser.
11. Claude API called with structured prompt: ECG findings + SHAP top-3 features + patient context → generates 3–5 sentence plain-language report per detected condition.
12. Output page renders: (a) Annotated ECG image with GradCAM overlay, (b) Condition list with probability progress bars and DETECTED/POSSIBLE badges, (c) SHAP contributor chart, (d) Plain-language AI report with English/Hindi toggle, (e) Recommended next action card.
13. 'Download PDF Report' button generates server-side PDF using WeasyPrint containing all of the above with app branding.
14. ECG session saved to history. User can view all past sessions in a timeline with thumbnail and top condition label.

## **5.3 Mode 3: Emergency Triage Flow**

1.  Persistent SOS button in top-right of global header. Large red button, visible on every page at all times.
2.  User taps 'I Feel Unwell Right Now' OR taps SOS header button.
3.  Full-screen triage questionnaire: 12 Yes/No questions with large touch-friendly buttons (min 44×44 px per WCAG). Questions listed in Section 3.2 clinical logic.
4.  Emergency Rule Engine runs client-side (JS) in parallel with server-side ML: IF (Q1=Y AND Q2=Y AND Q9=Y) → STEMI_HIGH_SUSPICION. IF ≥5 YES answers → EMERGENCY_LIKELY.
5.  Server-side: Random Forest model (trained on symptom combinations, calibrated with NICE CG95 rules) computes emergency probability score.
6.  Result routing: NORMAL → reassurance screen with tips. SEE DOCTOR TODAY → GP finder map + booking CTA. EMERGENCY → full emergency stack.
7.  EMERGENCY screen: Full-screen red background. Rendered components: (a) 'CALL 112 NOW' — large tel:112 link, (b) Live GPS location shared via Web Share API or copyable URL, (c) Nearest 3 hospitals map embed filtered by ICU/cath-lab availability, (d) Nearest ambulance panel with tel: links and ETA, (e) Calm instructions: 'Sit down. Do not drive. Chew aspirin if available and not allergic.' (f) Family Guardian push notification sent automatically if contacts configured.
8.  Offline fallback: Service Worker serves cached last-known emergency page with pre-loaded hospital list and tel: numbers even without internet.

## **6.3 ML Pipeline Architecture**

The ML pipeline has five parallel tracks that converge into a unified Risk Fusion layer:

- Track A — Tabular Risk Model: Vitals + demographics → feature engineering (BMI, pulse pressure, rolling averages) → LightGBM Classifier → ASCVD risk probability + SHAP explanation vector.
- Track B — ECG Signal Processing: ECG image → OpenCV + NeuroKit2 preprocessing → 12-lead signal extraction → resampling/normalization → 1D-SE-ResNet multi-label softmax (15 classes).
- Track C — ECG Transformer Ensemble: Same preprocessed signal → Transformer encoder (self-attention on 1D temporal patches) → probability vector → soft-vote ensemble with SE-ResNet output.
- Track D — ECG Explainability: Ensemble model → GradCAM saliency per lead → SVG overlay coordinates → served as JSON to frontend for interactive rendering.
- Track E — Report Generation: SHAP top-3 + ECG detected conditions + probabilities → structured prompt → Claude API (claude-sonnet-4-20250514) → plain-language paragraph per condition → stored in diagnoses.explanation_text.
- Risk Fusion Layer: Outputs from A + B/C → weighted formula → final risk tier + emergency flag → routed to correct screen.

# **9\. ML Model Development Plan**

## **9.1 Accuracy Enhancement Strategy**

The primary v2.0 accuracy upgrades over v1.0 are driven by three changes: (1) Transformer ensemble on top of SE-ResNet, (2) Indian cohort calibration for the tabular risk model, and (3) precision QTc measurement using NeuroKit2 beat averaging.

|     |     |     |
| --- | --- | --- |
| **Enhancement** | **Expected Gain** | **Implementation** |
| SE-ResNet + Transformer soft ensemble | +2–4% STEMI sensitivity | Train 1D Transformer (patch size 50, 8 heads, 6 layers) on PTB-XL. Soft-vote with SE-ResNet via learned α weight per condition. |
| Label-correlation loss function | +3–5% minority class F1 | Add Frobenius norm of correlation matrix difference to BCE loss: L = BCE + λ\|Corr(ŷ) − Corr(y)\|\_F. Captures known co-occurrences (LBBB+HF, STEMI+AFib). |
| Indian cohort calibration (INTERHEART SA) | +0.04 C-statistic | Re-fit LightGBM intercept on INTERHEART South Asia subgroup (n≈7,000). Platt scaling applied post-training. |
| NeuroKit2 QTc precision averaging | MAE from ~15ms → ~8ms | Average QTc over all detectable beats in each lead. Use Bazett, Fredericia, and Fridericia formulas; report median. |
| Focal Loss (γ=2) for rare conditions | +8–12% sensitivity on rare classes | Apply focal loss to WPW, Takotsubo, Hyperkalemia (prevalence <1% in training set). Combine with SMOTE-ENN oversampling. |
| Test-Time Augmentation (TTA) | +1–2% overall F1 | At inference, apply 3 augmentations (small time-shift, amplitude ±5%, Gaussian noise σ=0.01). Average probability vectors. |

# **12\. Regulatory, Compliance & Privacy**

## **12.1 Regulatory Classification**

- India: CDSCO Medical Device Rules 2017 — Class B Software as Medical Device (SaMD). Web delivery does not change classification.
- Quality Management: ISO 13485:2016 (medical devices QMS) + IEC 62304:2006 (medical device software lifecycle).
- Clinical Evidence: Document model performance via structured clinical evaluation report per IMDRF SaMD N41 guidelines.

## **12.2 Web-Specific Security Requirements**

- HTTPS enforced on all routes (HSTS header, min 1 year). No mixed content.
- Content Security Policy (CSP) header: restrict script-src to self + known CDNs. No inline scripts.
- JWT stored in httpOnly, Secure, SameSite=Strict cookies — never in localStorage/sessionStorage.
- Rate limiting on all API endpoints: 100 req/min per authenticated user, 10 req/min unauthenticated.
- OWASP Top 10 compliance — annual penetration test required before public launch.
- Subresource Integrity (SRI) hashes on all third-party scripts.

## **12.3 Data Privacy**

- India DPDP Act 2023: Explicit, granular digital consent before any health data collection. Users may withdraw and request deletion.
- Encryption: AES-256 for ECG data at rest in S3. TLS 1.3 for all API communication.
- Data minimization: Only store fields actively used in model inference. Raw ECG images deleted after 90 days unless user opts in.
- Audit logs: All PHI access logged in immutable RDS table. Retained 7 years per medical record norms.
- GDPR considerations for future EU expansion: data residency, right to erasure, DPA documentation.

## **12.4 Clinical Safety**

- All output must include disclaimer: 'This is an AI-assisted screening tool, not a substitute for professional medical diagnosis.'
- Emergency mode errs toward sensitivity — prefer false alarms over missed emergencies. Target: ≥97% sensitivity.
- Human-in-the-loop: Partner cardiologists review flagged edge cases monthly; feedback loop into model retraining.

This web-first architecture retains all the clinical power of the original mobile PRD while removing the single largest barrier to adoption: app-store installation. A React PWA served over HTTPS can reach any patient with a smartphone browser — no download required.
